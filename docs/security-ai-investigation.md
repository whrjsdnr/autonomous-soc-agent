# Phase 2-10: Security AI investigation execution

## Selection and execution are separate

```text
SecurityAISelector → SelectionPlan (no inference)
    → SecurityAIInvestigator.execute
    → whole-plan preflight
    → sequential current-registry revalidation and SecurityAI.predict
    → SecurityAIResult → create_ai_signal → AISignal
```

The selector remains unchanged and planning-only. The investigator receives a
registry, not an LLM, Tool executor, PolicyEngine, approval manager, or assessor.
Its only inference path is an exact registered SecurityAI wrapper. It never loads
artifacts, imports a model by name, creates handlers, or grants response authority.

```python
from soc_agent.security_ai import SecurityAIInvestigator

output = await SecurityAIInvestigator(registry=current_registry).execute(
    incident=state,
    selection_plan=plan,
    source_evidence={
        plan.steps[0].step_id: (evidence.evidence_id,),
    },
)
for step in output.steps:
    print(step.selection_step_id, step.status)
results = output.results
signals = output.signals
```

## Execution-time validation and registry drift

A selected plan is not authenticated execution authority. At entry the application
serializes/detaches/revalidates IncidentState, the full SelectionPlan, and the typed
source mapping. This catches invalid Pydantic bypass objects, extra fields, bounds,
duplicate IDs/model-input pairs, and invalid decision combinations. The plan incident
must match the actual state. Unknown selection-step IDs in the source mapping fail
before inference, including mappings supplied for an empty plan.

Every step then passes preflight before the first model is called:

1. Related Evidence IDs exist in this incident and are not duplicated.
2. The current registry resolves the exact selected name to a SecurityAI wrapper.
3. Name, version, task_type, and input_type exactly match the plan.
4. Current input schema validates the input with extra fields forbidden.
5. JSON serialization with aliases/defaults and the actual SecurityAIRequest
   envelope round trip preserve the plan's canonical input exactly.

Plan metadata is the selection-time snapshot copied from the selection registry.
Actual Result provenance is generated by the executing SecurityAI wrapper from its
own current metadata and validated request; the investigator does not manufacture
Result IDs or substitute plan metadata into a result.

A v1 selection presented to a registry containing v2 is BLOCKED, with zero inference.
Missing models and changed task/input type are likewise blocked. Registry removal
or replacement APIs are not added: callers/tests can supply a new registry at
execution. Descriptions are not compared because SelectionStep does not snapshot
them. Schema changes are detected when validation or canonical representation changes;
this is not schema/artifact fingerprinting. Implementations with identical metadata
and compatible input cannot be distinguished by the current contract.

Each step also repeats binding validation immediately before its call, after any
previous awaited inference. Thus whole-plan preflight avoids predictable partial
execution, while the per-step check catches drift observable between calls. The
resolved wrapper owns one invocation. Registry/schema setup must remain trusted;
this is not a lock against arbitrary concurrent Python mutation or an OS sandbox.
Pydantic validators/serializers must be deterministic and side-effect-free.

## Evidence provenance is an application assertion

`source_evidence: Mapping[UUID, tuple[UUID, ...]]` maps selection step IDs to related
source Evidence IDs. The mapping is detached before the first await. Omitting a step
means an empty reference tuple, consistent with Phase 2-8 inputs that may not originate
in Evidence. Unknown, foreign, and duplicate Evidence references block preflight.
Malformed incident snapshots containing foreign Evidence are rejected at entry.

The LLM does not provide this mapping; the application/caller supplies it. The current
input was proposed from summaries, so references mean **related source evidence**.
They establish existence and same-incident linkage, not that individual feature
values were extracted from those records. They do not prove input truth or model
accuracy. FeatureSet, FeatureExtractionRecord, InputFingerprint, and verified
preprocessing remain future work, not implementations in this phase.

## Result → AISignal, never Evidence

After successful inference, the investigator calls the existing create_ai_signal
factory with the real result, validated state, and step references. It does not
reconstruct Signal fields itself. The factory preserves source_result_id, incident,
model/version/task, prediction, optional confidence, scores, explanation, and source
Evidence references. Confidence is never derived from an anomaly score.

An inference result is a prediction, not an observation. The agent must not present
it as source-confirmed Evidence or automatically create a Hypothesis or assessment.
IncidentState remains unchanged because this operation adds analytical output rather
than observed facts or lifecycle decisions. Tool investigation still produces
Evidence independently; no Tool orchestration is modified here.

## Snapshots and status semantics

SecurityAIInvestigationResult is the immutable execution snapshot. It includes an
application investigation ID, selection_plan_id, incident_id, selection decision,
ordered step records, and UTC creation/completion timestamps. It does not redundantly
return unchanged IncidentState. Each SecurityAIInvestigationStep retains its immutable
selection snapshot, related source IDs, status, optional result/signal, attempt times,
and safe error type/message. selection_step_id exposes the selected step's identity.

Ordered `results` and `signals` are derived tuple properties. Serialization stores
records once under `steps`; it does not duplicate those collections. Step validators
check Result/Signal metadata, incident/payload binding, source result and Evidence
references, and timestamp consistency. The aggregate checks incident links, unique
identities, and stop ordering. These are consistency checks, not signatures proving
that an externally supplied snapshot was actually executed.

| Status | Meaning |
| --- | --- |
| PENDING | Not attempted because the pass stopped or preflight blocked another step |
| COMPLETED | Inference and Signal conversion succeeded |
| BLOCKED | Pre-inference binding/validation failed; no handler call for this step |
| FAILED | Inference/output validation or subsequent Signal conversion failed |

No RUNNING status or transition API is needed: this API returns a completed pass,
not live progress or resumable execution. started_at is present only for attempted
steps. completed_at on a blocked step denotes the block decision time, not inference.
No extra top-level outcome enum is introduced; decision and step statuses suffice.
NO_AI_NEEDED returns an empty successful no-op snapshot, even with an empty registry.
It is not incident closure or a benign classification.

## Stop and failure behavior

Malformed envelopes and mismatched incidents raise SecurityAIInvestigationError
before inference. Per-step preflight errors return a BLOCKED record at the offending
step; all other steps remain PENDING and no inference runs. For example, a stale
second model yields PENDING, BLOCKED, PENDING, rather than executing the first model.

Runtime steps execute strictly in selection order, at most once per execute call.
The first BLOCKED or FAILED step stops remaining execution. If model 1 succeeded,
model 2 failed, and model 3 was not reached, the snapshot is:

```text
1 COMPLETED → Result R1 + Signal S1
2 FAILED
3 PENDING
```

R1/S1 remain available. No rollback or silent discard occurs. If inference succeeded
but Signal conversion failed, the valid Result is retained on the failed step without
a Signal. Input rejection by the wrapper is BLOCKED; handler errors and invalid
prediction output are FAILED. Unexpected programming errors propagate intentionally.
Cancellation also propagates as in the existing Tool orchestrator; a cancelled call
does not return a partial snapshot and durable cancellation recovery is not provided.

There is no automatic retry or fallback because choosing another analysis or retrying
needs explicit future recovery/replanning decisions. A new caller execute invocation
is a fresh explicit attempt; there is no cross-call replay protection, resume state,
or idempotency guarantee. There is no parallel inference inside an invocation.
External concurrent invocations are not serialized by this coordinator.

Errors stored in snapshots use fixed public messages, never raw model inputs or
exception strings from handlers/conversion. Preflight messages are controlled by
application code. No raw traceback/input logging occurs here. Raised envelope errors
retain chained validation causes, which can contain sensitive values; callers must
not publish tracebacks indiscriminately. The snapshot retains canonical selected input
for traceability and therefore requires appropriate handling when stored or logged.

## Limits and future integration

Existing selection bounds cap execution to five steps. Inference deadlines, resource
budgets, durable audit storage, cancellation recovery, and artifact integrity are not
added here. These snapshots provide in-memory traceable outcomes, not a persistent
audit service. Existing SecurityAI adapter trust and timeout limitations still apply.
No dependency is added.

A future adaptive investigator can consume these separate signals and step failures
alongside observed Evidence to decide whether to collect more facts or propose a new
selection. It must preserve their semantic distinction, explicit budgets, provenance,
and deterministic governance. This phase does not call an LLM after results, fuse
models, change ThreatAssessment/severity/status, plan responses, train models, or
perform self-improvement.
